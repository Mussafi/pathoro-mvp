# Pathoro v0.11 — AI Opportunity Scout

Admin-only tool that turns "I have to manually find opportunity URLs" into
"Pathoro searches the web for candidates, I pick the real ones." **AI is not
finding events. It is scouting for route-relevant opportunity access
points.**

## Required environment variable

| Variable | Purpose |
|---|---|
| `TAVILY_API_KEY` | Server-only key for [Tavily](https://tavily.com)'s search API. Never prefixed with `NEXT_PUBLIC_`, never sent to the browser, never imported into a Client Component. |

Added to `.env.local.example` alongside the existing four v0.8 variables.
Same rules as those: never commit `.env.local`, never print or expose its
values.

**Why Tavily:** it's a search API built for exactly this kind of
AI-agent-driven web lookup — plain-language queries in, ranked results with
titles/URLs/snippets out, with built-in domain include/exclude filtering
(used here to keep Instagram/Facebook out of results at the source, not
just filtered after the fact). No scraping infrastructure to run ourselves.

## The scout flow

1. Admin opens `/admin/opportunity-scout`, enters a city, state, and a
   path/goal (free text — e.g. "become vegetarian"), and picks a **scout
   mode**:
   1. **Route-relevant opportunities** — the original v0.11 mode. Queries
      are route-type-biased (e.g. Real Openings biases toward "beginner
      class" / "workshop" phrasing) plus canonical-source-biased
      (organizer sites, Eventbrite, Luma, library/community calendars,
      volunteer boards). Still includes two rotated higher-agency query
      variants per **["Opportunity, not
      consumption"](MVP-LOCKED-PRINCIPLES.md#opportunity-not-consumption)**,
      and auto-detects gateway-signal language in the path/goal (trade,
      import/export, diaspora, "connect with...") to add a couple of bonus
      gateway queries — a light-touch version of mode 3, for when the admin
      hasn't explicitly switched modes but the goal calls for it anyway.
   2. **Hidden opportunity / leverage scout** — dedicated to
      **["the modern opportunity problem is not just finding
      events"](MVP-LOCKED-PRINCIPLES.md#opportunity-not-consumption)**.
      Every query in this mode is drawn from a pool of higher-agency
      opportunity patterns: resale/arbitrage, flea markets, estate sales,
      liquidation auctions, thrift sourcing, vendor market applications,
      makerspaces, repair/refurbishing entry points, apprenticeships,
      small-business grants, entrepreneur programs, local business gaps,
      import/export/sourcing communities, supplier relationships, local
      unmet needs, and places where builders/founders/operators gather
      (coworking spaces, maker communities). No route-type or
      class/workshop phrasing at all in this mode.
   3. **Gateway community scout** — dedicated to
      **["Gateway Communities"](MVP-LOCKED-PRINCIPLES.md#gateway-communities)**.
      Every query is drawn from the institution-type hint pool: local
      chambers of commerce, cultural associations, business improvement
      districts, language exchange groups, import/export workshops,
      sourcing/import communities, trade meetups, small business
      development centers, community business directories, and
      neighborhood organizations. *Structure-based, not identity-based*:
      the hints name institution **types**, never a specific ethnicity or
      culture — Pathoro responds only to what the admin typed as the
      path/goal, it never infers or assumes who someone is or which
      community they "should" belong to.
2. `POST /api/scout-opportunities` builds the query set for whichever mode
   was selected (`scoutMode: "route" | "hidden" | "gateway"`, defaulting to
   `"route"` if omitted).
3. Each query goes to Tavily's search API, with Instagram, Facebook, and
   Reddit excluded at the query level (`exclude_domains`) as well as
   filtered again in our own response handling, as defense in depth.
4. Pathoro classifies each result — a **rule-based heuristic classifier**,
   not a second AI/LLM call — producing:
   - *Route/source fit*: reuses the same `suggestRouteIdFromText()` keyword
     logic already shared with the v0.6 ingestion pipeline, plus hostname
     pattern matching, to produce a `sourceType`, a `likelyRouteId`, and a
     `confidence` rating.
   - *Opportunity category* (one field, 17 possible values — see below):
     checked most-specific-first, so a result only gets one label.
   - *Why this may be a real opportunity* (`whyThisMayFit`): which query it
     matched and whether it reads as a specific real page or a generic
     listing.
   - *What leverage it may create* (`leverageHint`): a one-sentence,
     category-driven note on what this could concretely open up — income,
     access, ownership, a network — distinct from just restating the
     category label.
   - *What next step it suggests* (`suggestedNextStep`): a one-sentence,
     category-driven suggestion for how someone would actually act on this.
   All four are visible on every candidate card, so an admin can favor
   higher-agency or bridge-building results without Pathoro silently
   deciding for them — a consumer-activity result still shows up, just
   clearly labeled as one, with its own (limited) leverage note.
5. The admin reviews the ranked candidate list and clicks **"Send to
   ingestion"** on the ones worth pursuing — this is the same query-param
   prefill pattern already used by the discovery queue
   (`/admin/opportunity-ingestion?sourceUrl=...&sourceType=...&city=...`).
6. `/admin/opportunity-ingestion` extracts the actual page (v0.6, unchanged)
   into a draft.
7. The admin edits/reviews the draft exactly as before (v0.7/v0.8.5's
   opportunity intelligence layer — why it appeared, what path it supports,
   what it may open next, etc.).
8. Approving saves a `status: "live"` row to Supabase through the existing
   v0.8 `POST /api/opportunities` flow — **nothing from the scout ever
   reaches Supabase directly.** Search results are candidates, not drafts,
   and drafts are never auto-approved.

Every step after "candidate found" is identical to the existing pipeline.
The scout only replaces the manual "where do I even start searching" step —
it does not add a second way for content to reach the public site.

## API contract

`POST /api/scout-opportunities`, admin-token protected (`x-admin-token`
header, same as `POST /api/opportunities`).

Request:
```json
{
  "city": "Austin",
  "state": "TX",
  "pathGoal": "become vegetarian",
  "routeId": "real-openings",
  "keywords": "beginner, cooking",
  "scoutMode": "route"
}
```

`scoutMode` is one of `"route"`, `"hidden"`, `"gateway"` — see the three
scout modes above. Optional; defaults to `"route"`.

Response:
```json
{
  "ok": true,
  "queriesUsed": ["become vegetarian beginner class Austin, TX", "..."],
  "candidates": [
    {
      "title": "Intro to Plant-Based Cooking",
      "url": "https://example.org/classes/intro-plant-based",
      "sourceName": "Example Community Kitchen",
      "snippet": "A hands-on beginner class covering...",
      "likelyRouteId": "real-openings",
      "whyThisMayFit": "Matches \"become vegetarian beginner class Austin, TX\" and reads as a hands-on class, not a one-off event listing.",
      "leverageHint": "Builds a skill that compounds if practiced beyond this one session.",
      "suggestedNextStep": "Sign up, then look for a way to keep practicing after it ends.",
      "opportunityType": "Class / Opening",
      "confidence": "high",
      "sourceType": "direct_submission",
      "canonicalSourceLikely": true,
      "opportunityCategory": "skill_building"
    }
  ]
}
```

`opportunityCategory` is one of: `consumer_activity`, `skill_building`,
`income_generating`, `access_point`, `ownership_path`, `proximity_builder`,
`credential_step`, `community_entry`, `compounding_opportunity`,
`gateway_community`, `bridge_person`, `place_based_network`,
`diaspora_route`, `trade_access_point`, `relationship_path`,
`resale_arbitrage` (v0.12), `small_business_opening` (v0.12) — 17 values.
It is **scout-response-only** — not persisted to Supabase's `opportunities`
table. An admin who approves a candidate is still saving the same
`Opportunity` shape as every other ingestion path (v0.8's schema,
unchanged); the category, `leverageHint`, and `suggestedNextStep` are
review aids, not new stored data. See "Do not change the database yet"
below.

On failure: `{ "ok": false, "error": "..." }` with an actionable message —
missing/invalid admin token (401), missing `TAVILY_API_KEY` (500, with setup
instructions pointing back at this doc), or missing required fields (400).

## What this deliberately does not do

- **No auto-publish.** A search result is a candidate, never a draft and
  never a live opportunity. It only becomes real by going through the
  unchanged ingestion → review → approve pipeline.
- **No Instagram/Facebook/Reddit scraping.** All three are excluded from
  search results at the query level (`exclude_domains`). A dedicated Reddit
  *signal* layer is a separate, still-unbuilt feature
  ([v0.9](V0.9-DISCOVERY-SOURCES.md)), not this one.
- **No database changes.** `opportunityCategory` lives only in the scout API
  response and the admin UI — it is not a new column on Supabase's
  `opportunities` table and is not sent by `POST /api/opportunities`. If a
  persisted category ever turns out to be worth it, that's a deliberate
  future migration, not a byproduct of this pass.
- **No accounts.** Admin-only, same temporary `ADMIN_TOKEN` shared-secret
  model as the rest of `/admin/*`.
- **No scheduled/automated crawling.** The scout only runs when an admin
  submits the form. There is no cron job, no background worker, no
  "run this search every night."
- **No robots.txt, paywall, or login bypass.** The scout only calls Tavily's
  search API — it never fetches candidate pages itself. When a candidate is
  sent to ingestion, the *existing* v0.6 extraction pipeline's robots.txt
  check and blocked-host guard apply exactly as they do today. "Avoid
  paywalled/login-only pages" at the search stage is best-effort (domain and
  snippet heuristics only, no page fetch) — the real backstop is that
  extraction and human review still happen before anything is a draft, let
  alone live.
- **No second AI/LLM call.** Classification is deterministic, rule-based
  logic shared with the existing ingestion pipeline — "AI" in "AI
  Opportunity Scout" refers to Tavily's search, not an added inference
  step. Keeps this dependency-light and avoids a second external API key.
- **No identity inference.** Gateway community search mode and its
  classification values respond only to the admin's own typed path/goal
  text. The scout never guesses, infers, or targets a person's ethnicity,
  culture, or community membership — see
  ["Gateway Communities"](MVP-LOCKED-PRINCIPLES.md#gateway-communities) for
  the full respectful-handling rules this is built on.

## Testing plan

- `POST /api/scout-opportunities` without a valid `x-admin-token` → 401.
- With a valid token but no `TAVILY_API_KEY` configured → 500 with a
  message that says what to set, not a generic failure.
- With both configured: a real search for Austin + "become vegetarian" +
  Real Openings Route returns a ranked candidate list, none from
  instagram.com/facebook.com/reddit.com.
- "Send to ingestion" on a candidate correctly prefills
  `/admin/opportunity-ingestion`.
- The full existing chain still holds end to end: ingestion extracts →
  admin approves → row saves to Supabase → `/route-planning` shows it →
  `/opportunity/[id]` opens it.
- A path/goal like "learn import/export" or "find diaspora business
  networks" triggers gateway community search mode (extra chamber-of-
  commerce/cultural-association/trade-meetup queries) and produces
  candidates classified into the gateway-community category values.
- Austin, TX + "build wealth" + hidden opportunity mode → resale/flea-
  market/grant-flavored queries and candidates, not classes.
- New York + "connect to China / import-export" + gateway community mode →
  chamber-of-commerce/trade/diaspora-flavored queries and candidates.
- Austin, TX + "become vegetarian" + route-relevant mode → still works as
  the original v0.11 baseline.
- `npm run lint`, `npx tsc --noEmit`, `npm run build`.

**Verified against a live Tavily key and Supabase project** (not just the
error paths): a real search for Austin + "become vegetarian" + Real Openings
Route returned 18 candidates from Eventbrite, ClassBento, Meetup, and
volunteer-board sources; a candidate was sent to ingestion, extracted from a
real Eventbrite page, reviewed, approved, and confirmed live on
`/route-planning` and `/opportunity/[id]`. Two real bugs were found and
fixed in the process: Tavily requires the API key via an `Authorization:
Bearer` header (not `api_key` in the request body), and a `reddit.com`
result was surfacing before Reddit was added to `exclude_domains`.
