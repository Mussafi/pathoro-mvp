# v0.30 — Dynamic Trail Map Drafts

Pathoro should not be limited to prebuilt Trail Maps. If someone searches for a path that doesn't have a curated template yet, Pathoro generates a starter draft on the spot instead of showing an empty "starting point" shell — but it never pretends that draft is verified. The product principle: Pathoro should be able to say *"I can start mapping this path now."*

## Map confidence

Every `TrailMapGoal` carries a `confidence` level (`lib/trailMapData.ts`):

| Level | Meaning |
|---|---|
| `template_verified` | Hand-built and product-reviewed. **Default** for all curated goals (therapist, nurse, plumber, etc.) via `getMapConfidence()` — they don't set this field explicitly. |
| `generated_starter` | Produced on the spot by the heuristic generator (or, later, an AI provider) from a user's search. Unreviewed. |
| `source_backed` | Future: a step above generated, short of hand-built — not assigned anywhere yet. |
| `community_strengthened` | Future: a path that has accumulated real trail markers, path guide dialogue, or scouted access points from actual users. Not implemented yet. |
| `verified_path` | Future: requirements confirmed against official sources (licensing boards, etc.). Not implemented yet. |

Only `generated_starter` has real UI treatment today — `MapConfidenceNotice` (`components/trailmap/MapConfidenceNotice.tsx`), shown on the Trail Map page, renders:

- A "Generated starter map" badge and the required disclosure: *"Pathoro created this first-pass map from your goal. Requirements and details should be verified from official sources."*
- A stronger licensing-specific line when the path looks regulated: *"Licensing requirements vary by state, institution, employer, union, and governing body. Treat this as a starting map, not official guidance."* Whether a path "looks regulated" is derived from existing branch data (`isLikelyRegulatedPath` checks `branchFactors.regulationBarrier`), not a separate field — no new data to keep in sync.
- A **"Strengthen this map"** row of CTAs — two are real, three are inert concept placeholders (not all need to be functional yet):
  - **Scout access points** — a real link to `/route-planning`, where the existing scout-request flow (`ScoutRequestCard`) lives. Trail Mode doesn't have its own routes/scout UI, so this points at the real one rather than duplicating it.
  - **Find someone ahead** — opens the real `PathGuideRequestModal`, the same component `PathGuideCard` uses, pre-filled from the generated goal's `pathGuide` recommendation.
  - **Verify requirements**, **Add trail marker**, **Start role dialogue** — inert (no write-path exists yet for any of these on a generated draft) — the product architecture for how a generated draft should invite verification over time, not a promise of what's live today.

## Generation architecture

**Trigger:** unchanged from before — `lib/goalSpecificity.ts`'s `mapGoalToTrailMapGoal` still runs first and always wins when it matches. Generation only kicks in when a search or `?goal=` param matches no curated goal, exactly where the old `TrailMapGenericShell` used to be the only option. A curated map is always better than a generated one, so `licensed plumber`/`electrician` etc. keep resolving to their hand-built templates untouched.

One fix that fell out of this: `mapGoalToTrailMapGoal`'s therapist pattern used to match any text containing "therapist" — including **"physical therapist assistant"**, a meaningfully different, lower-barrier support role. It now excludes matches containing "assistant" so that phrase reaches the generator instead of being swallowed into the curated Licensed Therapist map.

**Generator:** `lib/generatedTrailMaps.ts` exports `generateStarterTrailMap(goalText: string, context?: { city?, state?, userContext? })`, a pure, deterministic function returning a full `TrailMapGoal` — same shape the UI already knows how to render (milestones, branches, branch factors, tradeoffs, next steps, example trail notes, an embedded `pathGuide` recommendation). No network calls, no randomness.

It works by:

1. **Classifying the goal into one of 7 categories** via keyword patterns, chosen so branches feel specific to the kind of path rather than one generic template stretched over everything:
   - `licensed_trade` (HVAC technician, welder, barber, contractor, mechanic, ...)
   - `licensed_care` (physical therapist assistant, dental hygienist, social worker, dietitian, ...)
   - `creative_service` (wedding photographer, tattoo artist, interior designer, videographer, ...)
   - `local_business` (restaurant owner, coffee shop owner, cleaning business, landscaping business, ...)
   - `digital_knowledge` (UX designer, product manager, AI safety researcher, data analyst, ...)
   - `education_public` (school counselor, librarian, nonprofit director, ...)
   - `generic` — fallback when nothing else matches (e.g. "urban farmer")
2. **Picking 6–7 branches** for that category from `CATEGORY_BRANCHES` — each category has its own hand-written branch title list (e.g. `licensed_trade` gets "{Role} Helper", "Trade School Path", "Apprenticeship Path", "Residential {Role}", "Commercial {Role}", "Controls / Advanced Systems Path", "{Role} Business Owner Path"), so a generated map for "HVAC technician" reads like it's actually about HVAC, not a mad-lib. Each branch title maps to one of 9 shared archetypes (entry, certification, apprenticeship, specialization, independent, employed, business_owner, growth, oversight) that supply its `branchFactors`, tradeoffs, pitch, and next step — reused across categories so the scoring logic stays in one place.
3. **Building 8 milestones** — a licensing-flavored set for the two licensed categories, a portfolio-flavored set otherwise.
4. **Recommending a Path Guide** via `pathGuideForCategory` — `licensed_trade`/`licensed_care` get `"Licensed guide"` badged CTAs ("Talk to a licensed {role}"); `local_business` gets `"Talk to a {role} or operator"`; everything else gets `"Talk to a working {role}"` — all badged `"Verified experience"`. This reuses the same `GuideBadge` distinction the curated goals already use, not a new concept.
5. **Generating 3 example trail notes**, category-flavored (e.g. `licensed_care` leans on "shadow before enrolling" / "supervised hours take longer than advertised" / a safety warning; `local_business` leans on "work in the industry first" / thin margins / cash-reserve advice). `notesAreExamples: true` on the goal tells `TrailMapNotesPanel` to show an "Example trail notes" label and swap in copy that's explicit these aren't real user submissions.
6. Setting `confidence: "generated_starter"`.

**API:** `POST /api/trail-map/generate` (`app/api/trail-map/generate/route.ts`) wraps the generator — public, no admin token, no persistence. Every call is stateless. The Trail Map page (`app/trail-map/page.tsx`) calls this endpoint instead of calling the generator directly, with a short "Generating a starter map…" loading state, and falls back to the old `TrailMapGenericShell` only if the request itself fails (not the everyday path anymore).

**The AI seam:** `generateStarterTrailMap`'s signature and return type *are* the seam. A future AI-backed generator takes the same `(goalText, context)` input and produces the same `TrailMapGoal` shape — swapping one in means adding a provider branch inside the API route, not redesigning the data model, the generation flow, or any component that renders a `TrailMapGoal`. No LLM is wired up in v0.30.

## `TrailMapGoal.id` is now a plain string

Curated goals still use their fixed ids (`"therapist"`, `"plumber"`, ...) but the type itself was widened from the closed `TrailMapGoalId` union to `string`, since generated goals get a slugified id (e.g. `"wedding-photographer"`) that was never one of the ten known values. `TrailMapGoalId` still exists and is still used wherever a value is guaranteed to be one of the curated goals (the example-chip row, `getTrailMapGoal`).

`PathGuideCard`'s guide-recommendation lookup follows the same pattern: it prefers `goal.pathGuide` (set on every generated goal) and only falls back to its curated `GUIDE_CONTENT` table — keyed by the closed `TrailMapGoalId` — for known goals.
