# v0.30 — Dynamic Trail Map Drafts

Pathoro should not be limited to prebuilt Trail Maps. If someone searches for a path that doesn't have a curated template yet, Pathoro generates a starter draft on the spot instead of showing an empty "starting point" shell — but it never pretends that draft is verified.

## Map confidence

Every `TrailMapGoal` carries a `confidence` level (`lib/trailMapData.ts`):

| Level | Meaning |
|---|---|
| `generated_starter` | Produced on the spot by the heuristic generator (or, later, an AI provider) from a user's search. Unreviewed. |
| `source_backed` | Hand-authored by the product team with real-world knowledge, but not sourced from official data. **Default** for all curated goals (therapist, nurse, plumber, etc.) via `getMapConfidence()` — they don't set this field explicitly. |
| `community_strengthened` | Future: a path that has accumulated real trail markers, path guide dialogue, or scouted access points from actual users. Not implemented yet. |
| `verified_path` | Future: requirements confirmed against official sources (licensing boards, etc.). Not implemented yet. |

Only `generated_starter` has real UI treatment today — `MapConfidenceNotice` (`components/trailmap/MapConfidenceNotice.tsx`), shown on the Trail Map page, renders:

- A "Generated starter map" badge and the required disclosure: *"Pathoro created this first-pass map from your goal. Requirements and details should be verified from official sources."*
- A stronger licensing-specific line when the path looks regulated: *"Licensing requirements vary by state, institution, employer, and governing body. Treat this as a starting map, not official guidance."* Whether a path "looks regulated" is derived from existing branch data (`isLikelyRegulatedPath` checks `branchFactors.regulationBarrier`), not a separate field — no new data to keep in sync.
- A row of inert verification CTAs (Scout access points, Verify requirements, Find someone ahead, Add trail marker, Start role dialogue) — the product architecture for how a generated draft should invite verification over time. Deliberately not wired to real actions in v0.30.

## Generation architecture

**Trigger:** unchanged from before — `lib/goalSpecificity.ts`'s `mapGoalToTrailMapGoal` still runs first. Generation only kicks in when a search or `?goal=` param matches no curated goal, exactly where the old `TrailMapGenericShell` used to be the only option. Curated templates always win; a real plumber map is strictly better than a generated one, so `licensed plumber`/`electrician` etc. keep resolving to their hand-built templates untouched.

**Generator:** `lib/trailMapGenerator.ts` exports `generateTrailMapDraft({ goalText, city?, state?, userContext? })`, a pure, deterministic function returning a full `TrailMapGoal` — same shape the UI already knows how to render (milestones, branches, branch factors, tradeoffs, next steps, trail note examples, an embedded `pathGuide` recommendation). No network calls, no randomness.

It works by:
1. Classifying the goal text into a rough shape — `regulated`, `creative`, `business`, or `generic` — via keyword patterns.
2. Picking 6–7 branches for that shape from a fixed set of archetypes (entry, certification, specialization, independent, employed, business_owner, growth, oversight), each with its own baseline `branchFactors`, tradeoffs, and next step, interpolated with the derived role title.
3. Building 8 milestones (a licensing-flavored set for regulated shapes, a portfolio-flavored set otherwise).
4. Setting `confidence: "generated_starter"` and an embedded `pathGuide` recommendation badged `"Credential not verified"` — deliberately not `"Licensed guide"`, since the shape classification is a guess Pathoro hasn't confirmed.

**API:** `POST /api/trail-map/generate` (`app/api/trail-map/generate/route.ts`) wraps the generator — public, no admin token, no persistence. Every call is stateless. The Trail Map page (`app/trail-map/page.tsx`) calls this endpoint instead of calling the generator directly, with a short "Generating a starter map…" loading state, and falls back to the old `TrailMapGenericShell` only if the request itself fails.

**The AI seam:** `generateTrailMapDraft`'s signature and return type *are* the seam. A future AI-backed generator takes the same input and produces the same `TrailMapGoal` shape — swapping one in means adding a provider branch inside the API route, not redesigning the data model, the generation flow, or any component that renders a `TrailMapGoal`. No LLM is wired up in v0.30.

## `TrailMapGoal.id` is now a plain string

Curated goals still use their fixed ids (`"therapist"`, `"plumber"`, ...) but the type itself was widened from the closed `TrailMapGoalId` union to `string`, since generated goals get a slugified id (e.g. `"wedding-photographer"`) that was never one of the ten known values. `TrailMapGoalId` still exists and is still used wherever a value is guaranteed to be one of the curated goals (the example-chip row, `getTrailMapGoal`).

`PathGuideCard`'s guide-recommendation lookup follows the same pattern: it prefers `goal.pathGuide` (set on every generated goal) and only falls back to its curated `GUIDE_CONTENT` table — keyed by the closed `TrailMapGoalId` — for known goals.
